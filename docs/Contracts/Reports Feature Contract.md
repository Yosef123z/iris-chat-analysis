## 1. Goal

Add a **Report Generation with Recommendations** feature for the business dashboard.

The report should use the already-stored **interaction analysis results** generated by the AI after conversations end.

The goal is to let the business owner click a button in the dashboard and receive a clean report containing:

- Overall business/customer-service summary
    
- Sentiment overview
    
- Top customer intents
    
- Top discussed topics
    
- Common complaints/issues
    
- Key moments
    
- AI-generated recommendations
    
- Suggested actions with priority
    

---

## 2. High-Level Decision

The frontend must **not** call OpenAI directly.

The correct flow is:

```text
Frontend
→ .NET Backend
→ Backend aggregates stored analysis results
→ Backend sends aggregated data to AI service
→ AI service generates report + recommendations
→ Backend stores/returns report
→ Frontend displays report
```

This keeps:

- API keys secure
    
- Business logic centralized
    
- Rate limiting under backend control
    
- Report generation auditable
    
- Costs controlled
    
- UI simple
    

---

## 3. Ownership Split

## 3.1 .NET Backend Responsibilities

The .NET backend is responsible for:

1. Receiving report generation requests from the frontend.
    
2. Validating business access/authorization.
    
3. Reading analysis results from the backend database.
    
4. Aggregating numeric/statistical data.
    
5. Preparing a compact payload for the AI.
    
6. Calling the AI report-generation endpoint.
    
7. Storing the generated report if needed.
    
8. Returning the final report to the frontend.
    
9. Handling retries/errors/idempotency.
    
10. Preventing excessive report generation calls.
    

The backend remains the source of truth for:

- Businesses
    
- Interactions
    
- Analysis records
    
- Report records
    
- User permissions
    
- Generated report history
    

---

## 3.2 AI Service Responsibilities

The AI service is responsible for:

1. Receiving aggregated report data from the backend.
    
2. Generating a clear business report.
    
3. Generating practical recommendations.
    
4. Returning a structured response.
    
5. Avoiding hallucination beyond the provided data.
    
6. Returning controlled errors if the LLM provider fails.
    

The AI service should **not**:

- Read backend database directly.
    
- Store report records permanently.
    
- Generate reports from frontend requests directly.
    
- Receive raw API keys from frontend.
    
- Own report history.

## 4. Recommended Architecture

## 4.1 Backend Public Endpoint

The frontend calls the .NET backend:

```http
POST /api/businesses/{businessId}/reports/generate
```

Suggested request body:

```json
{
  "from": "2026-06-01T00:00:00Z",
  "to": "2026-06-30T23:59:59Z",
  "language": "ar",
  "includeRecommendations": true
}
```

Suggested backend behavior:

1. Validate current user owns or can access `businessId`.
    
2. Validate date range.
    
3. Query stored interaction analysis rows.
    
4. Aggregate the data.
    
5. Call AI service.
    
6. Save generated report.
    
7. Return report to frontend.
    

---

## 4.2 AI Internal Endpoint

The .NET backend calls the AI service:

```http
POST /api/v1/analysis/report/generate
```

Alternative acceptable name:

```http
POST /api/v1/reports/generate
```

Recommended endpoint name:

```http
POST /api/v1/analysis/report/generate
```

Reason: the report is generated from analysis results, so it belongs under the analysis domain.


---

## 7.3 Risk Level Values

Report risk level should be one of:

```text
low

high
critical
```

---

## 7.4 AI Rules

The AI must:

- Use only the data provided by the backend.
    
- Not invent numbers.
    
- Not invent sessions.
    
- Not mention unsupported metrics.
    
- Return practical recommendations.
    
- Keep Arabic clear and business-friendly.
    
- Keep English concise.
    
- Be suitable for a dashboard.
    
- Return JSON only.
    

---

## 8. Backend Aggregation Logic

The backend should calculate deterministic metrics before calling AI.

## 8.1 Basic Metrics

Calculate:

- Total sessions in period
    
- Total analyzed sessions
    
- Positive / Neutral / Negative counts
    
- Average sentiment score
    
- Count of each main intent
    
- Count of all detected intents
    
- Top topics
    
- Top key moments
    
- Total complaint sessions
    
- Total human-agent request sessions
    
- Total order-related sessions
    

---

## 8.2 Issue Detection

The backend can derive simple issue clusters from:

- `mainIntent = Complaint`
    
- negative sentiment
    
- topics like delivery, cold food, wrong order, payment, missing items
    
- key moments containing repeated problem phrases
    

This does not need to be perfect.

The AI can turn these aggregated issue groups into human-readable recommendations.

---

## 8.3 Data Volume Control

To avoid huge prompts:

- Send aggregate metrics.
    
- Send top 10 intents.
    
- Send top 10 topics.
    
- Send top 10 key moments.
    
- Send top 5 to 10 common issues.
    
- Send max 10 sample summaries.
    
- Do not send full raw chat transcripts unless needed later.

## 10. Report Caching / Idempotency

To avoid repeated AI calls:

If a report for the same:

- `businessId`
    
- `from`
    
- `to`
    
- `language`
    

already exists, backend can either:

1. Return the existing report.
    
2. Regenerate only if the user clicks “Regenerate”.
    
3. Regenerate if new analysis records exist after the report was created.
    

Recommended MVP behavior:

```text
Generate button creates a fresh report.
Recent generated reports can be stored and displayed.
```

Recommended improved behavior:

```text
If same period report exists, return it unless regenerate=true.
```

## 14. Error Handling

## 14.1 No Analysis Data

If no analysis data exists for selected period:

Backend should not call AI.

Return:

```json
{
  "message": "No analysis data available for this period.",
  "report": null
}
```

---

## 14.2 AI Service Failure

If AI report generation fails:

Backend returns:

```json
{
  "message": "Report generation failed. Please try again.",
  "details": "AI service unavailable"
}
```

Use appropriate HTTP status:

```text
502 or 503
```

---

## 14.3 Invalid Date Range

Return:

```text
400 Bad Request
```

---

## 14.4 Unauthorized Access

Return:

```text
401 or 403
```

## 18. Final Recommendation

Use AI for the recommendation/report-writing layer only.

Use backend deterministic logic for:

- counting
    
- grouping
    
- filtering
    
- sorting
    
- date ranges
    
- permissions
    
- storage
    

This is the cleanest architecture because:

- the backend owns data and security
    
- the AI handles language and recommendations
    
- the frontend stays simple
    
- OpenAI keys remain secure
    
- the feature is easy to demo
    
- the system remains maintainable
